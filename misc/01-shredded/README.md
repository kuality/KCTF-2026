## 문제 설명 (출제용)

> 퇴사한 직원의 자리에서 파쇄기 회수함을 통째로 확보했다.
> 조각 410장을 스캔했는데 스캔 품질이 엉망이다. 접힘, 얼룩, 기울어짐, 흐림이 섞여 있다.
>
> 눈으로 410장을 옮겨 적을 생각이라면, 그러지 않는 게 좋다.
>
> 포맷 명세는 `NOTES.txt` 에 있다.

첨부: `shredded.zip`

## 구성

```
shredded/
├── NOTES.txt              조각 라인 포맷 명세
└── fragments/
    ├── 0a1b2c3d.png       410장. 파일명은 무작위 — 순서 힌트가 아니다
    └── ...
```

조각 한 장에 한 줄:

```
BKD | BACOARGGREWDDWDYCGWWHCWA | OBA
IDX     DATA(24심볼)               CHK
```

- **알파벳**: `A B C D E G H K M N O R S W Y 4` 16심볼. 심볼 1개 = 4비트
- **IDX**: 3심볼. 심볼 순서가 곧 숫자 순서라 정렬만으로 복원된다
- **CHK**: `IDX + DATA` 27심볼에 대한 12비트 **위치 가중합**

410조각 × 24심볼 × 4비트 = **4,920바이트**다. 앞부분은
`recovery_log.txt`를 담은 deflate ZIP이고, 끝에는 전체 앞부분의 SHA-256에 묶인
`KCTFENC1` 암호문/HMAC 트레일러가 있다.

## 풀이

### 1. 전처리 후 일괄 OCR

```
grayscale → deskew(최소자승 기울기 추정) → 3배 확대 → tesseract --psm 7
```

**화이트리스트를 16심볼로 좁히는 것이 이 문제의 핵심 기교다.**
tesseract 는 화이트리스트 밖으로 답을 낼 수 없으므로, 알파벳이 작을수록 오답 선택지 자체가 사라진다. 실측:

| 알파벳 | 문자 오독률 | 24자 라인 정답률 |
|---|---|---|
| base32 `A-Z2-7` | 2.37% | 50% |
| hex `0-9A-F` | 0.21% | 62% |
| **safe16** `ABCDEGHKMNORSWY4` | **0.10%** | **94%** |

base32 는 `0/O`, `1/l` 은 없앴지만 `5→S`, `J→I`, `6→O`, `Q→O` 가 남는다.
safe16 은 그 혼동쌍을 실측 혼동행렬로 걸러낸 결과다.

### 2. 체크섬으로 실패 조각 국소화

1차 OCR 에서 **386/410 (94.1%)** 통과. 나머지 24장만 재시도 대상이 된다.
이 지점이 문제의 교육 포인트다 — 410장 전수 검수가 아니라 24장으로 좁힌다.

### 3. 실패 조각만 전처리 스윕

확대 배율·블러·이진화·배경 평탄화를 바꿔가며 9종 재시도 → **408/410** 확보.

### 4. 남은 2장 — 의도된 플레이어 경로: 그냥 눈으로 본다

여기가 이 문제의 요점이다. **410장은 손으로 불가능하지만 2장은 금방 확인할 수 있다.**
파이프라인이 사람의 일을 410 → 2 로 줄였고, 남은 2장은 저대비일 뿐 사람 눈에는
또렷하게 읽힌다. 솔버가 미해결 파일명과 누락 인덱스를 정확히 알려주므로
어디를 볼지 헤맬 일도 없다.

의도된 정석 풀이는 여기서 끝난다.

### 4-b. (참고) 레퍼런스 솔버는 이걸 자동화한다

`solve.py` 는 CI 검증용으로 사람 개입 없이 완주해야 해서 제약 탐색을 넣었다.
**플레이어가 이걸 할 필요는 없다.**

tesseract 의 실제 실패 양상은 글자 오독이 아니라 **필드 통째 누락**이었다.

```
BKD|BACOARGGREWDDWDYCGWWHCWA|          <- CHK 사라짐
AGD| |OWH                              <- DATA 사라짐
|4AMMOHSRAHWYOAWBADGSHSHO|OWD          <- IDX 사라짐
```

그래서 변형별로 **필드를 독립 수집**한 뒤 조합한다. 여기에 걸리는 제약이 강력하다:

- 남은 인덱스 집합이 `[83, 371]` 로 이미 알려져 있다
- 12비트 체크섬이 조합을 걸러낸다
- 최종 판정은 **ZIP CRC** 가 한다

후보가 백 개 단위로 나오므로 **편집 비용이 낮은 조합부터** 우선탐색한다. 실제 정답은 OCR 결과에서 1~2글자 떨어져 있을 뿐이라 **첫 조합**에서 CRC 를 통과한다.

### 5. 조립

정렬 → concat → 16심볼 디코드 → ZIP magic `PK\x03\x04` 확인 → CRC 검증 →
`SHA256(KCTFENC1 직전의 전체 prefix)`로 HMAC 확인 및 트레일러 복호 → 플래그 형식 확인.

```
$ python3 solve.py dist/shredded/fragments
[*] 조각 410장
[*] 1차 체크섬 통과 386/410 (94.1%), 재시도 대상 24장
[*] 재시도 후 확보 408/410, 미해결 2장
[*] 미복원 인덱스 [83, 371] — 제약 탐색으로 복구 시도
      1번째 조합에서 CRC 통과
FLAG: KCTF{0cr_p1p3l1n3_b34ts_th3_shr3dd3r}
```

전체 약 7초 (M-series, 12스레드).

### 전처리 변형은 측정해서 골랐다

70장 표본으로 변형별 체크섬 통과율과 합집합을 재서 스윕을 구성했다.

| 변형 | 통과 |
|---|---|
| blur 0.4 / otsu / blur 0.6+up4 | 68/70 |
| base (up3, 그대로) | 67/70 |
| up4 / up5 | 66/70 |
| 배경 평탄화 | 52/70 |
| fixed −12 | 51/70 |
| 평탄화 + psm 6 | 46/70 |
| 평탄화 + 언샤프 1.2 | 12/70 |
| 평탄화 + 언샤프 2.0 | 1/70 |
| psm 13 / fixed +12 | 0/70 |
| **합집합** | **70/70** |

언샤프를 넣으면 오히려 급락하고, psm 13 과 fixed +12 는 전멸이다. 감으로 넣었다면
스윕에 그대로 남았을 것이다. **합집합이 70/70 이라는 사실이 중요하다** — 모든 조각은
어떤 전처리로든 읽히므로, 스윕만 제대로 고르면 제약 탐색은 사실상 예비 수단이다.

## 설계 노트

### 왜 인덱스도 숫자가 아닌가
데이터를 OCR 안전 알파벳으로 해놓고 인덱스를 `037` 같은 숫자로 쓰면 도루묵이다.
**데이터 오류는 국소적이지만 순서 오류는 전역적**이라 훨씬 나쁘다.

### 왜 체크섬이 인덱스까지 커버하는가
데이터만 커버하면 인덱스 오독이 조용히 통과한다 — 위에서 지목한 최악의 오류 클래스가 그대로 빠져나간다.

### 왜 단순 합이 아니라 위치 가중합인가
단순 합은 `+3 / -3` 처럼 상쇄되는 오류쌍을 놓친다. 위치 가중을 넣으면 치환 1~2개와 자리바꿈까지 잡힌다.

### 왜 12비트(3심볼)인가
1심볼(1/16)이면 재시도 스윕 도중 **우연히 체크섬을 통과하는 오답**이 기댓값 수십 건 발생해 ZIP CRC 가 깨지고, 어디가 틀렸는지 알 수 없게 된다.
보정 실측에서 FALSE PASS 는 **0건**이었다.

### 왜 압축 스트림이 페이로드 전체를 채우는가
초안은 작은 ZIP + 패딩이었는데, 그러면 ZIP 이 앞쪽 십수 조각 안에 다 들어가서
**나머지 대부분을 읽지 않아도 플래그가 나온다.**
로그 텍스트를 압축해 거의 전 구간을 채우고, ZIP 중앙 디렉터리 뒤의 채움 바이트까지
포함한 전체 prefix를 SHA-256 키에 넣는다. 플래그 암호문과 HMAC은 맨 끝 트레일러에
둔다. 따라서 `unzip -p`로 로컬 엔트리만 읽거나 중앙 디렉터리를 생략해도 키를 만들 수
없고, 어느 구간 한 바이트가 틀려도 HMAC 검증을 통과하지 못한다.

### 열화 파라미터는 실측으로 정했다
`calibrate.py` 로 1차 체크섬 통과율을 측정하며 맞췄다. 목표 92~97%.

| | 통과율 |
|---|---|
| 초기값 (base32, 760px 캔버스, Otsu 이진화) | 52% |
| safe16 전환 | 71% |
| 캔버스 940px + 그레이스케일 유지 | 98.3% |
| **열화 재상향 (최종)** | **96.7%** |

> 캔버스 폭이 가장 큰 변수였다. 라인이 30심볼로 길어지면서 텍스트가 가장자리에
> 붙어 OCR 이 급격히 나빠졌다. 감이 아니라 수치로 재지 않았으면 못 찾았을 것이다.

## anti-shortcut 점검

| 항목 | 결과 |
|---|---|
| ① 번들 통째로 모델 투입 | 조각 이미지 410장 = 31.5MB. 단일 조각은 아무 의미 없고, 조립에는 정확한 순서 복원이 필요하다 |
| ② 기계적 우회 (grep / brute-force) | 플래그는 평문으로 존재하지 않고 정확한 4,920바이트 전체와 HMAC 검증이 있어야 복호 가능 |
| 무료 경로 | tesseract 5.5.3 + numpy/PIL 만으로 완주. VLM/유료 API 불필요 |
| 오류 감지 가능성 | 체크섬 → 인덱스 집합 무결성 → ZIP magic → CRC → 전체 페이로드 HMAC 인증 |

## 블라인드 검증

출제자 소스(생성기·솔버·설계문서)에 일절 접근할 수 없는 에이전트에게 배포물만 주고
일반 플레이어처럼 풀게 했다.

**결과: 독립 솔브 성공.** 27회 툴 호출, 수 분 소요.

| 단계 | 결과 |
|---|---|
| raw tesseract --psm 7 + 화이트리스트 | 355/410 |
| 배경 평탄화 + 행 프로파일 deskew + 3배 LANCZOS | +52 → 407/410 |
| 체크섬 기반 단일 치환/삭제 탐색 | +3 → 410/410 |

- **무료 도구로 충분했다.** VLM 은 이미 얻은 답을 확인하는 데 2장만 썼고, 없어도 완주 가능.
- 난이도 평가: *"스크립트를 짜면 LOW–MEDIUM, 손으로 옮겨 적으려 하면 HARD — 문제 설명이
  경고하는 그대로다. 공정하고 답답하지 않다."*

### 지적받아 고친 것

| 지적 | 조치 |
|---|---|
| `NOTES.txt` 에 **CHK 심볼의 자리 순서(MSB 우선)가 명시되지 않음.** IDX 규칙에서 유추해야 했다 | 명세에 "큰 자리가 왼쪽" 과 계산식을 명시. 조각 총수(0~409 연속)도 함께 명시 |
| 플래그 오타 — 파쇄기 문제인데 `sh4dd3r` (`shr3dd3r` 의 `r` 누락) | `KCTF{0cr_p1p3l1n3_b34ts_th3_shr3dd3r}` 로 수정 후 전량 재생성 |
| "체크섬은 좋은 판정 오라클이지만 약한 정정 도구다. 12비트에서는 단일 치환 후보가 여럿 나온다. 의도된 경로는 **다중 변형 합의**여야 한다" | 스윕을 실측으로 재구성(위 표). 스윕 단독으로 408/410 확보되어 제약 탐색은 예비 수단이 됨 |
| CRC가 틀린 ZIP도 `unzip -p`가 로그 끝의 플래그를 출력함 | 플래그를 ZIP 밖 인증 트레일러로 옮기고, 중앙 디렉터리·채움 바이트까지 포함한 전체 prefix를 키에 결합. 구간별 변조 회귀 테스트 추가 |
