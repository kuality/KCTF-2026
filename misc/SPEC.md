# 문제 1 — `shredded` (LOW)

## 배포물

```
shredded.zip
└── fragments/
    ├── 0001.png ... 0410.png     (파일명은 셔플된 무의미 순서)
```

파일명은 `a7f3e912.png` 처럼 랜덤 해시로 준다. **파일명이 순서 힌트가 되면 안 된다** — 순서는 이미지 안의 인덱스로만 복원되어야 한다.

## 조각 한 장의 내용

각 이미지에 한 줄:

```
AQ | MFRGGZDFMZTWQ2LKNRSXG5A | K
```

| 필드 | 내용 |
|------|------|
| `AQ` | 2글자 인덱스. **A–Z만 사용** (26² = 676 > 410). 순서 = 알파벳 순 |
| 가운데 | 24글자 base32 데이터 청크 (= 15바이트) |
| `K` | 1글자 체크섬 — **인덱스 2글자 + 데이터 24글자 전체**를 커버 |

### 왜 인덱스도 숫자가 아닌가
데이터를 base32로 해서 `0/O` 혼동을 막아놓고 인덱스를 `037` 같은 숫자로 쓰면 도루묵이다. OCR은 `0/8`, `3/8`, `5/6`을 혼동하고, 인덱스가 틀리면 **순서가 깨져서** 디버깅이 훨씬 어렵다(데이터 오류는 국소적이지만 순서 오류는 전역적이다).
A–Z 2글자로 하면 tesseract 화이트리스트가 `A-Z2-7|` 하나로 끝난다.

### 체크섬 (LOW 난이도의 핵심 장치)
`K = ALPHABET[(인덱스 2글자 + 데이터 24글자, 총 26문자의 값 합) mod 32]`

> **인덱스를 반드시 체크섬 범위에 포함시킬 것.** 데이터만 커버하면 인덱스 오독이 조용히 통과하는데, 이건 위에서 "전역적"이라고 지목한 바로 그 오류 클래스다. 인덱스를 포함하면 인덱스 오독도 그냥 재시도 버킷으로 떨어진다.

이게 있어야 솔버가 **어느 조각이 틀렸는지 국소적으로 안다.** 체크섬이 없으면 410장 중 3장이 틀렸을 때 어디가 틀렸는지 몰라서 문제가 LOW에서 벗어난다. 있으면:
- 1차 OCR → 체크섬 통과 395장, 실패 15장
- 실패한 15장만 다른 전처리나 VLM으로 재시도
- 이게 정확히 "AI를 배율기로 쓰는" 워크플로우

문제 설명에 힌트를 심는다: *"이 파쇄기는 각 조각에 검증 문자를 함께 찍는다."*

## 페이로드 — ZIP 확정

- `flag.zip` (내부에 `flag.txt`) 를 **정확히 6,150바이트로 패딩**
- base32 인코딩 → 9,840자 → 24자씩 410청크
- 디코드 성공 시 ZIP magic bytes `50 4B 03 04` + 내부 CRC 가 자가검증

**왜 텍스트가 아니라 압축 파일인가**: 플래그를 평문으로 넣으면 부분 복원만으로 눈대중으로 읽혀서 정확 복원 동기가 사라진다. 압축 파일은 한 바이트만 틀려도 깨져서 **전량 정확 복원을 강제**한다. PNG 대신 ZIP을 쓰는 이유는 ZIP이 엔트리별 CRC를 갖고 있어 **어느 부분이 깨졌는지 알려주기** 때문 — LOW 난이도에 맞는 친절함이다.

> **패딩 필수.** 410 × 15 = 6,150바이트 정확히 맞춰야 한다. 페이로드가 15의 배수가 아니면 마지막 base32 청크에 `=` 패딩 문자가 붙는데, **`=`는 `A-Z2-7` 화이트리스트에 없어서** tesseract가 못 읽는다. 생성기에서 ZIP 뒤에 무의미 바이트를 붙여 15의 배수로 맞춘다 (ZIP은 트레일링 바이트를 무시하므로 안전).

## 열화 파라미터

| 항목 | 값 |
|------|-----|
| 회전 | uniform(-3.0, +3.0)° |
| 가우시안 노이즈 | σ = 8 ~ 15 |
| JPEG 아티팩트 | quality 55~75로 저장 후 재로드, PNG로 출력 |
| 폰트 | 고정폭 3종 혼합 (DejaVu Sans Mono / Courier / Liberation Mono) |
| 폰트 크기 | 28~36px 랜덤 |
| 배경 | 종이 질감 + 커피 얼룩 원 1~2개 + 접힘 선 |
| 가장자리 | 찢긴 모양 마스크 |
| 대비 | 랜덤 감쇠 (0.6~0.9) |

**주의**: 얼룩을 문자 위에 겹치지 말 것. 복구 불가능한 조각이 생기면 체크섬으로도 못 살린다. 얼룩은 여백에만.

## 레퍼런스 솔버 절차

```
1. glob fragments/*.png
2. 전처리: grayscale → deskew(minAreaRect) → 2x upscale → Otsu threshold
3. tesseract --psm 7 -c tessedit_char_whitelist=ABCDEFGHIJKLMNOPQRSTUVWXYZ234567|
4. 파싱 → 체크섬 검증 → pass / fail 분리
5. fail 건: 전처리 변형(threshold 값 스윕) 재시도 → 그래도 실패하면 VLM
6. **인덱스 집합 무결성 검증**: 복원된 인덱스가 기대하는 410개 연속값과 정확히 일치하는가?
   중복/누락이 있으면 체크섬을 통과한 인덱스 오독이 남아 있다는 뜻 — 어느 조각인지 국소화된다
7. 인덱스 정렬 → 데이터 concat → base32 decode
8. ZIP magic bytes 확인 → 압축 해제 → flag.txt
```

**출제 전 측정할 숫자**: 1차 OCR 체크섬 통과율. 목표 **92~97%**.
- 100%면 열화가 약함 (재시도 루프가 무의미해져서 문제의 교육 포인트가 사라짐)
- 80% 미만이면 재시도 물량이 과해서 LOW가 아님

# 문제 2 — `inbox-triage` (LOW–MED)

## ⚠️ 앞선 설계의 결함과 수정

초안에서 "첨부 HTML을 난독화 해제하면 POST URL 파라미터에 플래그"라고 했는데 — **이러면 `grep -r 'KCTF{' .` 한 방에 끝난다.** 600통을 뒤질 이유가 사라져서 문제 자체가 성립하지 않는다.

수정: **플래그는 어디에도 리터럴로 존재하지 않는다.** 두 조각을 결합해야 나온다.

## 배포물

```
inbox-triage.zip
└── maildump/
    ├── 0001.eml ... 0600.eml
```

가상 회사 **Norite Systems** (`norite-systems.com`) 의 직원 메일함 덤프.

## 600통 구성

| 분류 | 통수 | 설명 |
|------|------|------|
| 정상 업무 | 505 | 회의 조율, 배포 공지, HR, 스프린트 리뷰, 내부 시스템 이름이 자연스럽게 등장 |
| 명백한 스팸/피싱 | 65 | 문법 어색, 뻔한 문구. 일부는 SPF fail. **`password`/`urgent`/`verify` 키워드 보유** |
| 회색지대 | 25 | 외부 벤더·마케팅. SPF fail이지만 무해 |
| **진짜** | 1 | 아래 |
| 디코이 (가짜 플래그) | 4 | 난독화 첨부 보유, 해제하면 `KCTF{n0t_th1s_0ne_...}` |

### 왜 grep이 안 통하는가
65통의 뻔한 피싱이 똑같은 키워드를 갖고 있어서 키워드 매칭은 후보를 60통 이상 뱉는다. SPF fail로 필터해도 30통 남는다.
**구분점은 문체와 맥락의 자연스러움** — 정규식이 못 하고 LLM이 잘하는 정확히 그 영역이다.

### 디코이 가짜 플래그 (anti-shortcut의 핵심)
4통의 디코이도 난독화된 첨부를 갖고 있고, 해제하면 그럴듯한 가짜 플래그가 나온다.
번들을 통째로 모델에 던지는 솔버는 **가짜 플래그를 자신 있게 제출한다.** 진짜를 찾으려면 결국 헤더 분석과 코퍼스 교차참조를 해야 한다.

## 진짜 한 통의 설계

```
From: "IT Helpdesk" <helpdesk@norite-systerns.com>
                                    ^^^ rn ≠ m  (호모글리프)
In-Reply-To: <CAF8x2...@norite-systems.com>   ← 0387.eml 의 실제 Message-ID
Subject: Re: VPN 인증서 만료 안내 (3/20)
Authentication-Results: spf=fail dkim=none dmarc=fail
Attachment: VPN_Cert_Renewal.html
```

특징 4가지, 난이도 순:
1. **SPF fail** — 흔함. 30통이 공유. 필터로는 부족
2. **호모글리프 도메인** `systerns` vs `systems` — 사람 눈에 거의 안 보임
3. **본문 톤이 자연스러움** — 다른 정상 메일에 나온 실제 내부 시스템 이름을 언급 (타겟티드 정찰의 증거)
4. **스레드 하이재킹** — `In-Reply-To`가 코퍼스에 실제 존재하는 정상 메일의 Message-ID를 참조

#### 4번의 정확한 불변식 (생성기가 지켜야 할 조건)
"원본 스레드에 이 답장이 없다"는 성립하지 않는다 — 하이재킹 메일 **자체가** 그 답장이기 때문이다. 실제로 탐지 가능한 불변식은 이것이고, 생성기는 이걸 코드로 강제해야 한다:

```
∀ 정상 스레드 T:
    participants(T) ⊆ @norite-systems.com  이고  Received 체인이 내부 전용
하이재킹 메일 H:
    In-Reply-To(H) ∈ Message-ID(T)         (스레드에 정상적으로 매달림)
    From(H) ∉ participants(T)               (그 스레드에 한 번도 없던 발신자)
    Received(H) 는 외부 홉을 포함            (스레드의 나머지는 내부 전용)
```

즉 **"내부 전용 스레드에 외부에서 처음 보는 발신자가 끼어든 유일한 지점"** 이 시그니처다.

**4번이 이 문제의 핵심이다.** 이건 600통 전체의 Message-ID 그래프를 봐야만 보인다. 사람이 손으로는 사실상 불가능하고, 스크립트+AI 조합이면 몇 분이다. "AI로 보안에서 이런 것도 가능하다"의 가장 좋은 시연.

## 플래그 조립 (2조각 결합)

첨부 `VPN_Cert_Renewal.html`:

```html
<script>
var _0=[0x2e,0x1b,0x47,...];               // 난독화된 바이트 배열
var k=/* 발신 도메인 */;                     // ← 키는 이 메일의 발신 도메인
function x(){ /* XOR 후 fetch POST */ }
</script>
```

- 난독화 해제 → 암호화된 바이트 배열 획득
- **XOR 키 = 스푸핑된 호모글리프 도메인 문자열** `norite-systerns.com`
- XOR → `KCTF{...}`

즉 **첨부를 찾는 것만으로는 부족하고, 스푸핑 도메인을 정확히 식별해야** 플래그가 나온다.

> **"어느 호스트명인지"를 추측시키지 말 것.** 초안의 `document.location.hostname`은 발신 도메인·정상 도메인·fetch 대상 IP 셋 다 후보라서 출제자 마음 알아맞히기가 된다.
> 대신 **검증 가능하게** 설계한다 — 솔버는 그 메일에 등장하는 도메인을 전부 후보로 넣고 하나씩 XOR해서 `KCTF{` 접두사로 확인하면 된다. 후보군이 작고 결정적이며, 호모글리프를 알아채는 아하 모먼트는 그대로 남는다. 정상 도메인으로 XOR하면 깨진 문자열이 나와서 솔버는 즉시 틀린 걸 안다.

`grep KCTF` → 디코이 4개의 가짜 플래그만 나온다.

## 코퍼스 생성 방법

505통의 정상 메일을 손으로 못 쓴다. 생성기가 할 일:
- 회사 설정(부서, 인물 12명, 내부 시스템 5개, 진행 프로젝트 3개)을 JSON으로 고정
- LLM으로 그 설정에 맞는 메일 본문 배치 생성 → 수동 검수
- 헤더(Message-ID, References, Date, Received 체인)는 **스크립트로 일관성 있게** 생성. 여기가 손으로 하면 반드시 깨지는 지점이고, 스레드 하이재킹 트릭이 성립하려면 Message-ID 그래프가 완벽해야 한다.

# 문제 3 — `intel-chain` (MED)

## 배포물

```
intel-chain.zip
├── BLUEHERON_TLPCLEAR_2026Q1.pdf     12페이지
├── sandbox/
│   ├── report_0442.json
│   ├── report_0517.json
│   └── report_0603.json
├── iocs.csv                          200행
└── traffic_summary.txt               ~5,000행
```

전부 합성. IP는 RFC 5737(`192.0.2.0/24`, `198.51.100.0/24`), 도메인은 `example.net` 계열.

## 4단계 체인

### 1단계 — 리포트에서 Wave 3 샘플 해시
p.7 "Campaign Timeline" 표에 wave 1~4의 dropper SHA256이 나열된다.
**p.6–8은 스캔 이미지 페이지로 만든다** — 텍스트 추출이 안 되고 OCR이 필요하다. (문제 1의 능력 재활용 = 카테고리 내 연결감)

Wave 3만 골라야 한다. 리포트 본문이 "3차 웨이브부터 C2 인프라가 교체되었다"고 서술한다.

→ `a3f9c1...` (Wave 3 dropper)

**검증 가능**: 잘못된 wave를 고르면 다음 단계에서 해당 해시를 가진 샌드박스 리포트가 없다. 즉시 안다.

### 2단계 — 샌드박스 리포트에서 C2 도메인
`report_0442.json` 의 `target.file.sha256` 이 일치.
`network.domains` 에 11개 도메인이 있다:

```json
{"domain": "telemetry.example.com",  "requests": 2},
{"domain": "update.example.org",     "requests": 1},
{"domain": "cdn-sync.example.net",   "requests": 47},   ← C2
...
```

C2 식별 근거: `network.http` 타임스탬프를 보면 **60초 간격 비콘**. 다른 도메인은 산발적.
LLM에게 "비콘 패턴을 가진 도메인" 물어보면 바로 나온다. 손으로도 되지만 JSON 800줄 × 3개라 지겹다.

→ `cdn-sync.example.net`

### 3단계 — IOC CSV에서 타임스탬프
```csv
indicator,type,campaign,first_seen,confidence
...
cdn-sync.example.net,domain,BLUEHERON,2026-03-14T09:21:44Z,high
...
```
200행 중 유사 도메인(`cdn-sync.example.org`, `cdn-sync2.example.net`)을 노이즈로 섞는다.

→ `2026-03-14T09:21:44Z`

### 4단계 — 트래픽에서 페이로드 복호화
`traffic_summary.txt` (약 5,000행):
```
2026-03-14T09:21:44Z  192.0.2.51:49883 -> 198.51.100.77:443  TLS  cdn-sync.example.net  len=284
  payload(b64): U1RfHhwbGRtZW50...
```

페이로드 = base64 → **AES-CTR (또는 RC4) 스트림 암호**.

> ### ⚠️ 반드시 반복키 XOR을 쓰지 말 것 — 체인이 통째로 우회된다
> 초안은 `base64 → 15글자 반복키 XOR`이었고 평문은 `KCTF{`로 시작한다. 이건 **crib-drag로 뚫린다**:
> 솔버가 `traffic_summary.txt`에서 `payload(b64)` 를 전부 grep → 디코드 → 각각에 `KCTF{`를 끌어보면
> **PDF도, 샌드박스 JSON도, IOC CSV도 열지 않고** 플래그가 나온다. 4단계 전부 무의미해진다.
>
> **수정**: 키를 스트림 키로 유도한다.
> ```
> key = SHA256("T1566T1059T1071")
> plaintext = AES-CTR-decrypt(key, nonce=0, payload)
> ```
> 솔버 코드는 여전히 5줄이지만 crib-drag가 죽고 체인이 실제로 하중을 받는다.
>
> **빌드 전 확인**: 5,000행 중 `payload(b64)` 행이 몇 개인가? 수백 개 미만이면 무엇을 하든 기계적 브루트포스가 싸다 — 스트림 암호로 가는 이유가 여기에도 있다.

**키 재료**: 리포트 p.9 ATT&CK 매핑 표에서 **Wave 3에 매핑된 기법 ID를 표 순서대로 이어붙인다.**
```
T1566  Phishing            (Wave 1,3)
T1059  Command Scripting   (Wave 3)
T1071  Application Layer Protocol  (Wave 3,4)
```
→ `T1566T1059T1071` → SHA256 → AES-CTR 키

> **서브테크닉 번호(`.001`)를 리포트 어디에도 쓰지 말 것.** `T1566.001`이 표에 있으면 `T1566T1059T1071`과 `T1566.001T1059.001T1071.001` 두 가지 연결 방식이 똑같이 그럴듯해져서 출제자 마음 맞히기가 된다. 베이스 기법 ID만 쓰거나, 연결 규칙을 리포트 본문에 명시한다.

**검증 가능**: 키가 틀리면 출력이 쓰레기. 맞으면 `KCTF{` 로 시작. 즉시 안다.

## 왜 이게 anti-shortcut을 통과하는가
- 어떤 단일 문서도 답을 담지 않는다 (4개 전부 조인 필요)
- 1단계는 PDF 스캔 이미지라 텍스트 추출이 실패한다
- 4단계 키가 리포트의 **다른 페이지**에 있어서, 체인을 따라오지 않으면 그게 키인 줄 모른다
- MITRE ATT&CK 기법 ID는 공개 정보라 안전하다

## MED 상한을 지키는 장치
매 단계가 **자기검증적**이다. 솔버가 3단계에서 막혀도 1~2단계가 맞았다는 걸 안다. 이게 없으면 "어디서 틀렸는지 모르는" MED가 HARD로 변한다.

# 출제 전 검증 체크리스트

| 항목 | 1 | 2 | 3 |
|------|---|---|---|
| `solver.py` end-to-end 실행 → 플래그 출력 | ☐ | ☐ | ☐ |
| anti-shortcut ①: 번들 통째로 모델 투입 → 플래그 안 나옴 | ☐ | ☐ | ☐ |
| anti-shortcut ②: **기계적 우회 경로** (grep / crib-drag / 브루트포스) 부재 | ☐ | ☐ | ☐ |
| 무료 도구(tesseract/스크립트)만으로 완주 가능 | ☐ | ☐ | ☐ |
| 실제 IP/도메인 미포함 (grep 검증) | ☐ | ☐ | ☐ |
| 오류 감지 가능성 (틀리면 솔버가 안다) | ☐ | ☐ | ☐ |
| 1차 정확도 실측치 기록 | 체크섬 통과율 92~97% | 후보 축소 후보군 크기 | OCR 성공 여부 |

**감이 아니라 수치로 기록한다.** AI 활용 문제가 죽는 지점이 정확히 여기다 — 출제자가 모델과 눈으로 한 번 맞춰보고 실제 정확도를 끝내 모르는 것.

### anti-shortcut은 두 가지 실패 모드가 따로 있다
- **①  모델 우회** — 번들을 통째로 LLM에 던지면 답이 나온다. 문제 2의 디코이 가짜 플래그가 이걸 막는다.
- **②  기계적 우회** — 모델이 전혀 개입하지 않는 grep / crib-drag / 브루트포스로 체인을 건너뛴다. 문제 3의 초안 반복키 XOR이 정확히 이 케이스였다.

①만 점검하면 ②를 놓친다. **문제마다 "체인을 건너뛰는 순수 기계적 경로가 있는가"를 별도로 자문한다.**
