# KCTF 2026 — MISC

"AI로 보안에서 이런 것도 가능하다" 를 보여주는 5문제.
AI는 **정답을 알려주는 오라클이 아니라, 사람이 손으로는 못 할 대량 작업을 처리하는 도구**로 쓰인다.

|---|---|---|---|---|

## 관통하는 원칙

### 1. AI는 배율기여야 한다, 오라클이 아니라

AI 테마 MISC가 실패하는 패턴은 늘 같다. "AI면 이거 읽을 수 있지!"로 만들고 나면,
그건 곧 **"AI가 그냥 끝까지 풀어버릴 수 있다"**는 뜻이다.

문제 1이 이 원칙의 모범이다. 파이프라인이 **410장을 2장으로 줄이고**, 남은 2장은
사람 눈에 또렷하다. 손으로는 불가능한 일을 가능하게 만들되, 답 자체를 주지는 않는다.

### 2. anti-shortcut은 실패 모드가 두 개다

| | 실패 모드 | 이 카테고리에서 실제로 발생한 사례 |
|---|---|---|
| ① | **모델 우회** — 번들을 통째로 LLM에 던지면 답이 나온다 | 문제 2의 미끼 가짜 플래그가 이걸 막는다 |
| ② | **기계적 우회** — 모델이 전혀 개입하지 않는 grep / crib-drag / 브루트포스 | 문제 3 초안의 반복키 XOR이 정확히 이 케이스였다 |

**①만 점검하면 ②를 놓친다.** 그리고 ②가 더 자주, 더 조용히 문제를 죽인다.
설계 단계에서 잡은 것만 셋이다.

- 문제 2: XOR 키가 그 메일 안의 도메인 → 첨부 grep + 도메인 대입으로 600통 분류가 증발
- 문제 3: 반복키 XOR + `KCTF{` 접두사 → crib-drag로 4단계 전부 우회
- 문제 3: 키 재료가 기법 문자열 단독 → 2만 회 대입으로 샌드박스·IOC 단계 우회

### 3. 감이 아니라 수치로 정한다

출제자가 모델과 눈으로 한 번 맞춰보고 **실제 정확도를 끝내 모르는 것** — AI 활용 문제가
죽는 지점이 정확히 여기다. 측정하지 않았으면 못 찾았을 것들:

| 발견 | 실측값 |
|---|---|
| base32는 OCR에 부적합. 화이트리스트가 작을수록 오답 선택지가 사라진다 | 문자 오독 2.37% → **0.10%** |
| 캔버스 폭이 최대 변수. 텍스트가 가장자리에 붙으면 급락 | 통과율 71% → **98.3%** |
| 언샤프 마스크는 오히려 크게 해롭다 | 68/70 → **12/70** |
| ATT&CK 표의 `1, 3` 표기는 OCR로 전멸. `waves 1 3`이면 완벽 | `AEN)` → **정확** |

마지막 것은 특히 중요했다. 감으로 골랐다면 `1, 3`을 그대로 뒀을 것이고,
**키 재료를 만들 수 없어 문제 3이 성립하지 않았다.**

### 4. 오류를 솔버가 감지할 수 있어야 한다

조용히 틀린 답이 나오면 안 된다. 다섯 문제 모두 객관적 수렴 지점을 넣었다.

- 문제 1: 체크섬 → 인덱스 집합 무결성 → ZIP magic → CRC → 전체 4,920바이트 HMAC 인증
- 문제 2: 키가 틀리면 UTF-8 디코드부터 실패
- 문제 3: 매 단계가 자기검증적 (잘못된 wave → 해당 해시의 샌드박스 리포트가 없다)
- 문제 4: 각 유출문의 4/4 사실 일치는 정확히 하나, 차점은 3/4
- 문제 5: 각 플랫폼의 3/3 경험 일치는 정확히 하나, 차점은 2/3

문제 3에서 이건 난이도 상한 장치이기도 하다. 자기검증이 없으면
"어디서 틀렸는지 모르는" MED가 HARD로 변한다.

### 5. 무료 경로를 보장한다

유료 VLM이 있어야만 풀리면 pay-to-win이다. 다섯 문제 모두 무료 경로로 완주를 확인했다.

| 문제 | 필요 도구 |
|---|---|
| 1 | tesseract + PIL/numpy |
| 2 | **표준 라이브러리만** (`email`, `hashlib`, `re`) |
| 3 | tesseract + pypdf |
| 4 | 표준 라이브러리 + 사람이 만든 동의 표현 표 |
| 5 | 표준 라이브러리 + 사람이 만든 의미 피벗 표 |

### 6. 실제 IOC를 쓰지 않는다

TI 문제는 실제 APT 데이터를 쓰고 싶어지지만, 실제 IP·도메인을 넣으면
**솔버들이 대회 중에 진짜로 찔러본다.**
IP는 RFC 5737(`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`),
도메인은 `example.*` 예약 네임스페이스만 썼다. 자동 검사로 위반 0건을 확인했다.

## 블라인드 검증

다섯 문제 모두, **출제자 소스(생성기·솔버·설계 문서)에 일절 접근할 수 없는 에이전트**에게
배포물만 주고 일반 플레이어처럼 풀게 했다. 이게 가장 값진 단계였다 —
자기 문제를 자기가 검증하면 아는 답을 향해 걸어가게 된다.

실제로 나온 지적과 조치:

| 문제 | 지적 | 조치 |
|---|---|---|
| 1 | `NOTES.txt`에 CHK 심볼의 자리 순서가 명시되지 않아 유추해야 했다 | 명세에 계산식 명시. 명세는 유추 대상이 아니어야 한다 |
| 1 | 플래그 오타 — 파쇄기 문제인데 `sh4dd3r` | `shr3dd3r`로 수정 후 전량 재생성 |
| 1 | "체크섬은 좋은 판정 오라클이지만 약한 정정 도구다. 의도된 경로는 다중 변형 합의여야 한다" | 전처리 스윕을 실측 재구성 → 스윕 단독 408/410 |
| 1 | CRC가 깨진 ZIP도 `unzip -p`가 로그 끝 플래그를 출력하고, 로컬 엔트리만 파싱하면 중앙 디렉터리를 생략 가능 | 플래그를 ZIP 밖 트레일러로 옮겨 전체 prefix SHA-256/HMAC에 결합하고 압축 본문·중앙 디렉터리·padding·암호문·tag 구간별 변조 테스트 추가 |
| 2 | **너무 싸게 풀렸다.** 불리언 두 개(`첨부 보유` → 66, `In-Reply-To` 존재 → 1)로 끝나 그래프 분석이 통째로 우회됨 | 미끼 스팸 32통도 답장 형태로. 누적 필터가 66 → 33 → 15 → 1이 되어 마지막 조건에서야 확정 |
| 2 | 진짜만 `References`가 없어 그 자체가 비명처럼 튄다 | 진짜에 부모 하나만 담고, 정상 답장 40%도 같은 형태로 |
| 2 | 문제 설명의 "65통"이 필터 정답을 흘린다 | 설명에서 개수 제거 |
| 2 | ZIP만 받은 모델은 정상 복호되는 미끼 6개와 진짜의 선택 기준을 잃음 | `INCIDENT_BRIEF.txt`에 기존 내부 대화 침투·외부 발신자·필터 통과라는 객관적 목표 동봉 |
| 4 | 초안은 정답 12개가 pair/triple 빈도와 Hamming 중심성으로 전부 드러남 | 각 유출 후보군을 완전한 `3^4` 격자로 재구성. 972개 전부 동일한 1·2·3필드 빈도, 차수, 원시/ZIP 크기를 갖게 함 |
| 5 | 초안은 문장 희귀도·압축 크기·파일 위치만으로 4/5 ID가 노출됨 | 입력과 다음 피벗을 각각 완전한 `3^3` 격자로 만들고, 본문 900바이트·무압축 ZIP·중간 위치로 균형화 |
| 5 | 꼬리 문장 형식을 일반화하면 다시 4/5 ID가 노출됨 | 두 번째 격자까지 문장 빈도 서명을 `(9,9,9,9,9,9)`로 통일. 최종 회귀에서 모든 단계가 27-way tie |
| 5 | 인공 접미사가 없는 행만 거르면 단계마다 27→8로 감소 | 모든 꼬리 사실에 같은 접미사를 적용. 개수도 27개 전원 동일하고, 제거 후 빈도 서명도 전원 동일 |
| 5 | 접미사 수정본은 개별 레코드 zlib 크기만으로 4/5 ID가 1위 | 의미 표현 길이를 균형화하고 컨테이너 원문·공백 제거본·본문의 재압축 순위를 모두 5~23위로 감사 |

문제 2는 **한 번 통과한 뒤 다시 뒤집힌** 사례다. 풀렸다는 사실만으로는 부족하고,
**어떻게 풀렸는지**를 봐야 한다.

## 잔여 위험 원장 (출제 전 필독)

**하드닝을 여기서 멈췄다.** 이유와 남은 위험을 정직하게 적는다.

### 의도된 경로와 실측 비용

| 문제 | 의도된 경로 | 레퍼런스 솔버 |
|---|---|---|
| 1 | 전처리 스윕 OCR → 체크섬으로 실패 국소화 → 남은 2장은 눈으로 | 약 7.5초 |
| 2 | 600통 파싱 → Message-ID 그래프 → 불변식 → 조상 체인 → 복호 | 약 2.7초 |
| 3 | 스캔 OCR → 샌드박스 비콘 분석 → IOC 정확 일치 → 트래픽 → 복호 | 약 3.1초 |
| 4 | 유출문 사실 정규화 → 972개 브리핑 4필드 교집합 → ID 해시 | 0.1초 미만 |
| 5 | 5개 플랫폼에서 세 경험씩 의미 조인 → ID 체인 해시 | 0.1초 미만 |

### 막지 않기로 한 대체 경로

| 문제 | 경로 | 실측 비용 | 완화 |
|---|---|---|---|
| 2 | 첨부 66개 중 체인이 해석되는 25개를 전부 복호 | 약 65초 | 그럴듯한 플래그 7개가 나오나, **진짜만 인증통과+낮은스팸** 이라 objective 하게 1통으로 수렴 (찍기 없음) |
| 3 | IOC 도메인 × 샌드박스 해시를 전부 대입 | 약 2분 (8코어) | 근접 오답 키로 만든 미끼 페이로드가 함께 나온다 |
| 5 | 공백 제거 MARKET 행을 bzip2로 재압축하면 정답이 우연히 1위 | 한 단계만 1/27 | 다른 네 플랫폼에서는 재현되지 않고 전체 체인·플래그를 정하지 못한다 |

**이 두 경로는 원리적으로 막을 수 없다.** 키 재료가 코퍼스 내용에서 유도되는 한
후보 공간은 유한하고 열거 가능하다. KDF 스트레칭(12,000,000회)은 비용을 올릴 뿐
경로를 없애지 못한다.

> 그래서 방어의 축을 바꿨다. **"대입을 막는다" 가 아니라 "대입에 성공해도 답이
> 하나로 안 좁혀지게 한다".** 두 문제 모두 근접 오답 키에서 그럴듯한 플래그가
> 나오므로, 결국 의도된 분석을 해야 판별된다.
>
> 대가가 있다. 미끼 플래그가 그럴듯해진 만큼 **오답 제출이 늘 것을 전제해야 한다.**
> 오답 제한이나 감점 정책이 있는 플랫폼을 권한다.

### 감사 도구가 잡는 것과 못 잡는 것

`02-inbox-triage/audit.py` 는 두 축으로 검사한다.

- **불리언 축** — 값싼 속성 17종의 1·2·3개 조합 전수 검사
- **유일값 축** — 파생값 11종이 정답에서만 유일한지 (헤더 순서, 본문, 바이트수 등)

**못 잡는 것**: 새로 시드된 코퍼스의 우연한 통계적 이상치. 1/600 바늘에는 언제나
*어떤* 구별 속성이 존재하고, 재생성할 때마다 그 속성이 바뀐다.
`SEED` 를 바꿔 재생성했다면 **감사를 다시 돌리고 아래 항목을 눈으로 확인할 것.**

블라인드 검증이 실제로 잡아낸 축들 — 재생성 시 직접 확인:

| 축 | 확인 방법 |
|---|---|
| Date 분포 | 미끼가 특정 기간에 몰리지 않는가 |
| 답장 지연 | 부모→자식 시간차가 정답만 튀지 않는가 |
| 헤더 직렬화 위치 | 정답에만 적용되는 후처리 경로가 없는가 |
| 본문 군집 | 정답만 유일한 문체 군집을 이루지 않는가 |

### 검증 이력

문제 2 블라인드 검증 5라운드. 매 라운드 **에이전트는 문제를 풀었고**, 매번 *푼 방식* 이
문제였다. 문제 4·5도 같은 에이전트가 소스 없이 반복 검증했고, 최초 배포물의 기계적
지름길을 실제로 사용한 뒤 재생성본에서 같은 공격과 일반화 공격을 다시 실행했다.

| 라운드 | 발견 | 성격 |
|---|---|---|
| 1 | 불리언 2개로 600→1 | 설계 결함 |
| 2 | 키 공간 열거 가능 (39,600회, 0.1초) | 설계 결함 |
| 3 | 정답만 헤더 직렬화 위치가 다름 | 생성기 버그 |
| 4 | 정답만 본문 문체가 다름 | 배제했던 판별자의 귀환 |
| 5 | 같은 원인의 다른 발현 (References·Date·지연) | **증상만 고쳤던 것** |

5라운드가 가장 값진 교훈이었다. 3라운드에서 `del` + 재추가로 헤더가 밀리는 문제를
고쳤는데, 원인을 *"특정 헤더의 위치"* 로 이해했지 *"정답에만 적용되는 후처리 경로"*
로 이해하지 않아 다른 헤더에서 같은 패턴을 반복했다.

**멈춘 이유**: 4·5라운드의 발견이 전부 같은 클래스였고, 각 수정이 RNG 를 흔들어
다음 빌드에 다른 우연한 이상치를 만든다. 이 루프는 수렴하지 않는다.

배포물의 압축 해제본은 커밋하지 않는다 (`.gitignore`). 배포되는 것은 각 `dist/*.zip` 이다.

전체 회귀 검사는 프로젝트 가상환경에서 한 번에 실행한다.

```bash
.venv/bin/python test_challenges.py -v
```

이 테스트는 다섯 ZIP을 새 임시 디렉터리에 풀어 레퍼런스 솔버로 완주하고, 배포 구성
수량·플래그 평문 부재·1번 전 구간 변조 실패·2/4/5번 지름길 감사를 함께 확인한다.
