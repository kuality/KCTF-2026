## 풀이

### 1. 왜 grep 이 안 통하는가

키워드로는 못 좁힌다. 명백한 스팸 65통이 `password`, `urgent`, `verify` 를 똑같이 갖고 있다.
SPF 로도 못 좁힌다 — 미끼 다수와 외부 벤더가 이미 `spf=fail` 이다.

| 조건 | 남는 후보 |
|---|---|
| 답장이다 | 381통 |
| 발신 도메인이 사내가 아니다 | 103통 |
| Received 체인에 외부 홉이 있다 | 113통 |
| 난독화 첨부가 있다 | 66통 |

어느 하나로도 안 된다. 조합해도 마지막 조건 전까지는 안 좁혀진다.

| 누적 필터 | 남는 후보 |
|---|---|
| 난독화 첨부 보유 | 66통 |
| ＋ `In-Reply-To` 가 있다 | 43통 |
| ＋ 그 값이 코퍼스 안에서 해석된다 | 25통 |
| ＋ 매달린 스레드가 내부 전용 **이고** 발신자가 외부다 | **1통** |

마지막 줄에서야 1통이 된다. 그래프를 실제로 세워야만 도달한다.

### 2. 구조 불변식 — Message-ID 그래프

600통의 `Message-ID` / `In-Reply-To` 로 스레드 그래프를 세우면 유일한 시그니처가 나온다.

```
H 는 답장이다                                    (In-Reply-To 가 코퍼스 내 메일을 가리킨다)
AND thread(H) − H 의 참여자가 전원 사내 도메인    (내부 전용 스레드)
AND From(H) 의 도메인이 사내가 아니다             (외부인)
```

**"내부 전용 스레드에 외부에서 처음 보는 발신자가 끼어든 유일한 지점"** 이다.

교집합 = **1통**. 세 조건 각각으로는 수십~수백 통이 남지만 교집합은 유일하다.

> **참여자는 발신자만이 아니라 수신자까지 포함해야 한다.**
> 발신자만 보면 벤더 스레드에서 벤더가 처음 답장하는 순간이 하이재킹과 구조적으로
> 똑같아 보인다 (실제로 이 버그 때문에 초안 솔버가 5통을 잡았다).
> 벤더는 애초에 루트의 `To` 에 들어 있는 정식 참여자다.

### 3. 기계는 보는데 사람은 못 보는 것

```
From: "IT Helpdesk" <helpdesk@norite-systerns.com>
                                     ^^^ rn ≠ m
```

이 문제의 교훈이 여기 있다. 호모글리프는 **사람 눈에는 거의 안 보이지만 문자열 비교에는
100% 걸린다.** 눈으로 600통을 넘기는 접근이 실패하는 이유이자, 코드로 그래프를 세우는
접근이 성공하는 이유다.

### 4. 첨부 난독화 해제

```html
<script>
var _c=[40,102,117,...];
var _s="";for(...){_s+=String.fromCharCode(_c[i]);}
(new Function(_s))();
</script>
```

풀면 키 유도 방법이 **명시적으로** 적혀 있다 (출제자 마음 알아맞히기가 아니다):

```js
var host = "norite-systerns.com";
var blob = [ ... ];

// beacon key material = EVERY Message-ID on this message's ancestor chain,
// ROOT FIRST, ending with the message we replied to. Each id exactly as it
// appears in the header, angle brackets included, joined with ",".
// Then "|" then host.
//
//   MATERIAL = "<root>,<...>,<parent>" + "|" + host
//   key      = sha256(MATERIAL)
//
// (operator note: walk In-Reply-To all the way up. our own In-Reply-To is
//  mid-thread and the References we send is truncated on purpose, so the
//  chain is not readable off any single header.)

// keystream = sha256(key + str(i)) concatenated, i = 0,1,2,...
// plain[j] = blob[j] ^ keystream[j]
```

### 5. 스레드 루트까지 거슬러 올라가기

하이재킹 메일의 `References` 에는 **직전 부모 하나만** 들어 있다. `In-Reply-To` 도
스레드 중간을 가리킨다. 루트를 얻으려면 부모를 따라 끝까지 걸어야 한다.

> `References` 를 아예 빼면 "유일하게 References 가 없는 메일" 이 되어 그 자체가
> 비명처럼 튄다. 정상 답장의 40%도 부모 하나만 담게 해서 형태를 묻어두었다
> (현재 References 없는 답장 48통, 부모 하나만 담은 것 196통).

```
키 재료 = <루트>,<...>,<부모>  +  "|"  +  <위조 도메인>
```

**루트 하나가 아니라 조상 체인 전체다.** 루트 로컬파트만 쓰면 코퍼스의 Message-ID
600개 × 첨부 66개 = 39,600회 대입이 **0.1초**에 끝난다 (블라인드 검증 실측).
체인 전체는 조합적으로 열거할 수 없다.

### 6. 복호

SHA256 카운터 모드 키스트림으로 XOR. 순수 파이썬 15줄이면 재현된다.

```
$ python3 solve.py dist/inbox-triage/maildump
[*] 전체 600통
      답장 381통 / 외부 도메인 103통 / 외부 Received 113통 / 첨부 66통
[*] 세 조건의 교집합: 1통
[*] 하이재킹 메일: 0548.eml
[*] 위조 도메인: norite-systerns.com  (정상: norite-systems.com)
[*] 조상 체인 4단계 -> 루트 <eb8d2821a146dd4d@norite-systems.com>
FLAG: KCTF{thr34d_h1j4ck_h1d3s_1n_th3_gr4ph}
```

0.3초.

## 설계 노트

### 판별자를 '문체' 로 잡지 않았다

초안은 "진짜만 본문 톤이 자연스럽다" 를 구분점으로 삼았다. 이건 못 쓴다.
505통을 한 번의 템플릿 생성으로 만들면 그 판별자는 **어느 쪽으로든 무너진다** —
전부 기계적으로 읽히거나, 진짜만 유독 잘 쓰인 티가 난다.
무엇보다 **측정할 수가 없다.** 문제 1이 수렴한 건 통과율이라는 숫자가 있었기 때문이다.

그래서 판별 기준을 Message-ID 그래프 불변식으로 바꿨다.
**생성기가 코드로 강제할 수 있고 솔버가 검증할 수 있다.** 문체는 양념일 뿐이다.

`solve.py` 는 불변식을 만족하는 메일이 정확히 1통인지 **단언한다.** 그게 풀린다는 증명이다.

### 근접 오답을 일부러 심었다

두 조건이 각각 단독으로는 안 통하게 만들어야 교집합에 의미가 생긴다.

| 심은 것 | 탈락하는 조건 |
|---|---|
| 외부 벤더가 이미 참여 중이던 스레드에 답장 (14 스레드) | '내부 전용' |
| 내부 직원이 처음 끼어드는 답장 (22통) | '외부인' |
| 스팸이 존재하지 않는 Message-ID 에 답장 (18통) | '해석 가능' |
| 스팸이 벤더 스레드에 매달린 답장 (14통) | '내부 전용' |

## 블라인드 검증 1차 — 그리고 드러난 큰 구멍

출제자 소스에 접근할 수 없는 에이전트에게 배포물만 주고 풀게 했다.
**풀렸다. 그런데 너무 싸게 풀렸다.**

에이전트의 보고를 그대로 옮기면:

> 통했고 — 솔직히 **너무 쉽게 통했다**: 첨부 보유로 600 → 66이 한 번에 되고,
> 그 66통 중 `In-Reply-To` 를 가진 것을 고르면 한 줄로 66 → 1이 된다.
> 불리언 두 개. 점수화도 순위화도 필요 없었다.

즉 **그래프를 세울 필요가 아예 없었다.** 이 문제의 핵심이 통째로 우회된 것이다.
추가로 두 가지를 더 지적받았다.

| 지적 | 조치 |
|---|---|
| 첨부 66통 중 답장은 진짜 하나뿐 → `In-Reply-To` 존재 여부가 곧 정답 | 미끼 스팸 32통도 답장 형태로 만들었다. 18통은 존재하지 않는 Message-ID 를 가리키고(해석 실패), 14통은 외부 참여자가 있는 벤더 스레드에 매달린다('내부 전용' 탈락) |
| 진짜만 `References` 가 없어서 그 자체가 비명처럼 튄다 | 진짜에 부모 하나만 담은 `References` 를 넣고, 정상 답장의 40%도 같은 형태로 만들었다 (현재 References 없는 답장 48통, 부모 하나만 196통) |
| 문제 설명의 "65통" 이 필터 정답을 흘린다 — 66통을 찾으면 복호 전에 이미 맞았음이 확인된다 | 설명에서 개수를 뺐다 |

### 수정 효과

| 누적 필터 | 수정 전 | 수정 후 |
|---|---|---|
| 난독화 첨부 보유 | 66통 | 66통 |
| ＋ `In-Reply-To` 가 있다 | **1통** | 43통 |
| ＋ 코퍼스 안에서 해석된다 | — | 25통 |
| ＋ 매달린 스레드가 내부 전용이다 | — | **1통** |

에이전트가 정확히 짚은 대로 고쳤다. 이제 마지막 조건 전까지 후보가 남고,
그 조건은 그래프와 참여자 집합을 실제로 계산해야만 판정된다.

### 유지하기로 한 것

같은 보고에서 **잘 동작한다** 고 평가받은 부분은 그대로 뒀다.

- SPF/DKIM/DMARC 를 미끼와 정상 양쪽에 고루 뿌린 것 — 판별력 0으로 확인됨
- `X-Norite-Spam-Score` 가 무상관인 것 (판별력 0)
- 미끼 가짜 플래그가 정직한 것 — `keep looking` 이라고 말해줄 뿐 플레이어의 런을
  끝내려 들지 않는다

### 키를 두 번 바꿨다 — 열거 가능성이 핵심이다

| | 키 재료 | 어떻게 뚫렸나 |
|---|---|---|
| 초안 1 | 그 메일 안의 도메인 | 첨부 grep + 도메인 대입. 600통 분류가 통째로 증발 |
| 초안 2 | 루트 Message-ID 로컬파트 + `@` + 위조 도메인 | 로컬파트 600 × 첨부 66 = 39,600회, **0.1초** |
| 현재 | 조상 Message-ID 체인 전체 + `\|` + 위조 도메인 | 조합적으로 열거 불가 |

초안 2는 "코퍼스에 그대로 존재하지 않는 조립물" 이라 안전하다고 판단했었다.
**그게 틀렸다.** 조각이 코퍼스에서 나오면 조립 규칙이 알려진 순간 열거 가능하고,
난독화된 첨부가 그 규칙을 친절히 알려준다.

교훈은 이렇다. **"코퍼스에 없는 문자열" 은 안전의 근거가 아니다.
"조합적으로 열거할 수 없는 문자열" 이어야 한다.**

### 첨부는 66통이 갖는다 — 그리고 구별이 안 된다

5통만 첨부를 가지면 "첨부 있는 메일 찾기" 로 후보가 5개가 되어 분류가 사라진다.
65통의 미끼도 첨부를 갖는다. 여기서 더 중요한 건 **구조적으로 튀지 않아야** 한다는 것:

| 초안의 구멍 | 조치 |
|---|---|
| 진짜만 문자코드 난독화, 미끼는 `eval(atob(...))` → 66개 중 1개가 즉시 튐 | 전부 동일 래퍼로 통일 |
| 진짜만 파일명이 `VPN_Cert_Renewal.html` 로 유일 | 파일명 풀 9종을 미끼와 공유 |
| 진짜만 `host` 가 사내 유사 도메인 | 미끼에도 유사 도메인 5종 투입 (현재 30통) |
| blob 길이가 튐 | 미끼 blob 길이를 28~48 로 분산 |

점검 결과: 난독화 형태 66/66 동일, **유일한 파일명 없음, 유일한 host 없음.**

### 미끼 가짜 플래그

미끼 4통은 자기 Message-ID 로 유도한 키로 가짜 플래그를 싣고 있다.
번들을 통째로 모델에 던지는 솔버가 이걸 집는다.
눈으로 보면 가짜인 게 명확하도록 썼다 (`KCTF{th1s_1s_a_d3c0y_keep_looking}`) —
스코어보드 스프레이를 유발하지 않기 위해서다.

### 반복키 XOR 을 쓰지 않은 이유

평문이 `KCTF{` 로 시작하므로 반복키 XOR 은 crib-drag 로 즉사한다.
SHA256 카운터 모드는 그 경로가 없고, 솔버 구현 부담도 15줄이다.

## anti-shortcut 점검

| 항목 | 결과 |
|---|---|
| ① 모델 우회 (번들 통째 투입) | 미끼 4통의 가짜 플래그를 집는다 |
| ② 기계적 우회 (grep) | 평문 `KCTF{` 등장 **0통**. 1차 난독화를 풀어도 미끼 가짜만 나온다 |
| ② 기계적 우회 (첨부 골라내기) | 66통 전부 동일 구조. 파일명·host·blob 길이 어느 것도 진짜를 특정하지 못한다 |
| 무료 경로 | 표준 라이브러리만 사용 (`email`, `hashlib`, `re`). 외부 의존성 0 |
| 오류 감지 가능성 | 키가 틀리면 복호 결과가 UTF-8 디코드부터 실패. `KCTF{` 접두사로 확인 |

### 지름길 감사 (`audit.py`)

블라인드 검증에서 세 번 다 **"풀린다" 가 아니라 "너무 싸게 풀린다"** 가 문제였고,
매번 사람이 눈으로 찾아낸 탓에 매번 다른 걸 놓쳤다.
그래서 값싼 불리언 속성 17종을 나열하고 **1개·2개·3개 조합을 전수 검사** 하는
스크립트를 만들었다.

```
$ python3 audit.py
--- 단일 속성으로 1통이 되는가 ---   없음
--- 두 속성 조합(AND)으로 1통이 되는가 ---   없음
--- 세 속성 조합(AND)으로 1통이 되는가 ---   3건
```

남은 3건은 전부 `발신 도메인 사내유사`(호모글리프 식별)를 포함한다 —
그건 막아야 할 지름길이 아니라 **의도된 아하 모먼트**다.

## 블라인드 검증 3차 — 생성기 버그 2건

3차에서는 감사 스크립트가 못 잡는 종류가 나왔다. **속성이 아니라 생성기 아티팩트** 였다.

| 지적 | 원인 | 조치 |
|---|---|---|
| `X-Norite-Spam-Score` 헤더가 **진짜 메일에서만 맨 뒤에 있다.** 600통 중 1통 — grep 한 줄로 끝 | 진짜만 `del` 후 재추가하는 코드 경로를 탔다 | 스팸점수를 `build()` 파라미터로 받아 모든 메일이 같은 경로·같은 위치로 |
| 미끼 65통이 전부 `192.0.2.x` 인데 진짜만 `203.0.113.201` | 미끼와 진짜의 IP 생성 코드가 달랐다 | 세 대역을 공통 풀로 |
| 첨부의 주석은 `key = sha256(MATERIAL)` 인데 구현은 중간 해시 없이 `sha256(MATERIAL + i)` | 명세와 구현 불일치 | 반복 KDF 로 통일하고 주석을 실제 구현에 맞춤 |
| 제목으로 묶고 날짜로 정렬하면 조상 체인이 복원된다 (1,529회) | 답장 시각이 항상 증가했다 | 스레드 내 답장 시각의 45%를 거꾸로 흔들어 날짜순 ≠ 답장순 |
| 미끼 blob 이 순수 난수라 **복호되는 순간 정답이 확정** 된다 | 미끼 가짜 플래그가 다른 규칙으로 암호화되어 사실상 없는 것과 같았다 | 미끼도 **문서화된 규칙을 자기 조상 체인에 적용** 해 암호화 |

> **생성기 아티팩트는 속성 감사로 안 잡힌다.** `audit.py` 는 "이 메일이 어떤
> 속성을 갖는가" 를 보지, "직렬화 결과의 바이트 배치가 남들과 같은가" 는 안 본다.
> 사람(또는 블라인드 에이전트)이 원본 파일을 직접 훑어야 나오는 종류다.

### 미끼가 이제 실제로 작동한다

문서화된 규칙을 후보 25통에 **기계적으로 다 돌리면** 이렇게 나온다:

```
0005.eml  KCTF{wr0ng_0ne_try_th3_gr4ph}
0113.eml  KCTF{thr34d_h1j4ck_h1d3s_1n_th3_gr4ph}   <- 진짜
0582.eml  KCTF{th1s_1s_a_d3c0y_keep_looking}
0587.eml  KCTF{d3c0y_n0t_th3_r34l_fl4g}
0591.eml  KCTF{n0t_1t_ch3ck_th3_thr34d}
```

복호가 더 이상 공짜 판별이 아니다. 어느 것이 진짜인지는 **불변식으로 판정해야** 한다.

### 키 열거 문제는 KDF 로 처리했다

키 재료가 코퍼스 구조에서 유도되는 한 열거는 원리적으로 막을 수 없다.
3차에서 측정된 후보 공간은 *"어떤 메일의 루트→자신 경로"* 600개 × 첨부 66개 =
**39,600회, 0.07초** 였다. 2차에서 지적받은 것과 숫자가 똑같다.

그래서 산수를 바꿨다 — 반복 해시 **12,000,000회**:

| | 후보 수 | 비용 |
|---|---|---|
| 정직한 경로 | 1 | **1.8초** |
| 무차별 대입 | 39,600 | 약 **20시간** |

*"전부 대입한다"* 를 *"분석해서 후보를 좁힌다"* 로 강제한다.

--- 단일 속성으로 1통이 되는가 ---   없음
--- 두 속성 조합(AND)으로 1통이 되는가 ---   없음
--- 세 속성 조합(AND)으로 1통이 되는가 ---   3건
```

남은 3건은 전부 `발신 도메인 사내유사`(호모글리프 식별)를 포함한다 —
그건 막아야 할 지름길이 아니라 **의도된 아하 모먼트**다.

감사로 실제 잡아낸 것:

| 걸린 지름길 | 조치 |
|---|---|
| `수신자 2명 이상` AND `수신자 전원 사내` → 1통 | 미끼 45%에 사내 다중 수신자 부여 |
| `첨부 보유` AND `본문에 한글` → 1통 (미끼가 전부 영문이었다) | 스팸 본문 55%를 한글로 |
| `첨부 보유` AND `References 1개` AND `수신자 전원 사내` → 1통 | 사내 주소를 위조해 내부 스레드에 답장하는 미끼 10통 추가 |
